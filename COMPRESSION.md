# Compression

Goal: a 30x30 tile should be stored in about 500 characters. Currently it's over 6000. The bottom of this file has an example problem URL.

Proposal:
- Change cs into a dictionary where each entry encompasses an entire tile: main-shape (orth-cross, diag-cross, star) and materials for main, taco1, taco2, taco3, taco4. Each material can be absent. For orth-cross the tacos will be in a particular order, e.g. nw, ne, se, sw. For diag-cross the tacos will also be in order, e.g. n, e, s, w. For star the tacos that we emit will all be absent. If there are two diag-crosses next to each other, we will emit it so the shared tacos between them are identical. Upon reading a star, we'll ignore tacos. Upon reading a diag-cross, we'll let the last one win, but also report a conflict/error.
- Entry 0 in the cs index is "blank" and doesn't need to be serialized.
- Each entry in cs also has an optional "prefix cs index" with the meaning "that tile first, then this one". This allows for arbitrary-length sequences. I think we'll likely only emit max 2, except conceivably we might do longer sequences of blanks. We will require prefixIndex < currentIndex, a cheap way to prevent cycles.
- We'll do VARINT for CS indexes, starting at 4 bits for the common indexes, falling back to 8 then 16 bits. For the four bits, a value of 15 means the next 8 bits are an index. For those 8 bits, a value of 255 means the next 16 bits are an index.
- We'll specify grid origin, width and height. We'll read CS indexes to fill a row up to width. If they go over the row width, the rest for that row are ignored and we start on the next one. (Motive: so that long blank-sequences can be used at the tail of rows). If we end up not filling the entire width+height of the grid, the tailing ones are assumed blank. (Motive: when users start, they won't have filled everything)

## Findings so far

Generated by `node scripts/compression-prototype.mts`.

The current best direction is:

- Use a single-cell `cs` dictionary only. Do not use prefix/sequence entries.
- Store the prototype payload byte-by-byte rather than with 2-bit/4-bit fields.
- Store dictionary fields column-by-column: all shapes, then all main materials, then taco columns.
- Use locked global material ids directly in the dictionary; do not preserve the old local `cs` table.
- Store settings as fixed binary fields rather than JSON.
- Gzip the whole byte-oriented payload, then base64url encode it for the URL.

Gzip is better at finding the irregular row and tile repetition than the prototype's explicit sequence dictionary. The sequence dictionary makes raw bytes smaller, but makes gzip results worse.

Stream-only comparison:

| Format                            | Raw bytes | Raw chars | Gzip bytes | Gzip chars |
| --------------------------------- | --------: | --------: | ---------: | ---------: |
| Single-cell bit-packed stream     |      1052 |      1403 |        307 |        410 |

Interpretation:

- The byte-token stream gives gzip cleaner symbols, and gzip compresses it slightly better than the bit-packed stream.
- The single-cell stream is larger before gzip, but smaller after gzip than the sequence-token stream.
- Explicit sequence entries remove local repetition before gzip can see it, while adding dictionary overhead.
- The columnar dictionary beats row-wise dictionary storage after gzip because it gives gzip low-entropy runs of similar fields.
- Binary settings and direct global material ids cut out the remaining obvious JSON overhead.

## Raw binary payload layout

All multi-byte integers are big-endian. The raw payload is always gzipped as one byte sequence, then base64url encoded. The URL does not support an uncompressed/raw payload form.

Primitive types:

```text
uint8      1 byte, unsigned
uint16     2 bytes, unsigned
int16      2 bytes, signed two's-complement
index      if value < 255: uint8 value
           otherwise:      uint8 255, then uint16 value
```

Current full payload:

```text
Header
  uint8  magic                // 0x53, ASCII "S"
  uint8  formatVersion        // 1

Settings
  uint8  view                 // 0=straight, 1=diagonal
  uint8  grid                 // 0=invisible/underneath, 1=visible/on top
  uint16 roomAreaWidth        // inches
  uint16 roomAreaHeight       // inches
  uint8  placeholderSize      // inches
  int16  gridOffsetXTimes2    // half-inch units
  int16  gridOffsetYTimes2    // half-inch units
  uint8  groutColorId         // 1..9 in GROUT_COLORS order
  uint8  groutWidth           // sixteenths of an inch

Grid window
  int16  originCol
  int16  originRow
  uint16 width                // grid cells
  uint16 height               // grid cells

Dictionary
  index  entryCount           // excludes implicit blank entry 0
  uint8  shape[entryCount]
  index  mainMaterial[entryCount]
  index  taco0Material[nonStarEntryCount]
  index  taco1Material[nonStarEntryCount]
  index  taco2Material[nonStarEntryCount]
  index  taco3Material[nonStarEntryCount]

Stream
  uint16 tokenCount
  index  token[tokenCount]
```

Dictionary entry 0 is always implicit blank and is never serialized. The serialized dictionary entries are numbered `1..entryCount`.

Shape values:

```text
0 = blank              // currently only used for implicit entry 0
1 = orthogonal cross
2 = diagonal cross
3 = star
```

Material values:

```text
0     = absent taco/material
1..52 = locked tile material id, in the order listed below
```

For normal tile entries, `mainMaterial` is nonzero. For taco-only placeholders, `shape` may be `orthogonal cross` or `diagonal cross` with `mainMaterial = 0`; in that case no main tile is created, but the taco columns are still applied.

Taco column order depends on the main shape:

```text
diagonal cross:   taco0=n,  taco1=e,  taco2=s,  taco3=w
orthogonal cross: taco0=nw, taco1=ne, taco2=se, taco3=sw
star:             omitted from all taco columns
```

The stream scans the rectangular grid window row-major: left-to-right within each row, top-to-bottom across rows. Each stream token is a dictionary entry index.

Settings storage:

```text
uint8  view                 // 0=straight, 1=diagonal
uint8  grid                 // 0=invisible/underneath, 1=visible/on top
uint16 room area width      // inches
uint16 room area height     // inches
uint8  placeholder size     // inches
int16  grid X offset * 2    // half-inch units
int16  grid Y offset * 2    // half-inch units
uint8  grout color id       // 1..9 in GROUT_COLORS order
uint8  grout width          // sixteenths of an inch
```

## Material lock-in

`src/constants.ts` now assigns a stable integer id to each tile material. The compression prototype reads those ids from `constants.ts`.

The current material list in `src/constants.ts` has 52 tile materials. With `0` reserved for absent, every material fits in one byte as an integer `1..52`.

For the example URL, the existing local `cs` table maps to global material ids as follows:

| Local material index | Material     | Global material id |
| -------------------: | ------------ | -----------------: |
|                    1 | `verd`       |                  8 |
|                    2 | `white`      |                 10 |
|                    3 | `mud`        |                  3 |
|                    4 | `fawn`       |                  4 |
|                    5 | `orchard`    |                  7 |
|                    6 | `terracotta` |                  5 |

Comparison:

| Material strategy                         | Material bytes | Dictionary bytes | Raw bytes | Raw chars | Gzip bytes | Gzip chars |
| ----------------------------------------- | -------------: | ---------------: | --------: | --------: | ---------: | ---------: |
| Current local `cs` as JSON                |             54 |              169 |      2357 |      3143 |        520 |        694 |
| Local `cs` as byte sequence of global ids |              7 |              169 |      2310 |      3080 |        492 |        656 |
| Direct global material ids in dictionary  |              0 |              169 |      2303 |      3071 |        489 |        652 |
